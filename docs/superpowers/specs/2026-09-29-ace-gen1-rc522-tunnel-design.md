# ACE Pro (Gen 1) — туннель RC522: дизайн

Дата: 2026-09-29
Статус: дизайн на ревью
Связанные материалы: `REPORT-EN.md`, `README-RU.md` (маршруты «мост» и CFW-врезка),
репозиторий `Godless50/ACE-PRO-v1.-NFC-UID`, обсуждение `decay71/multiACE#137`.

## 1. Задача

Сделать так, чтобы Gen 1 ACE Pro отдавал считыватель RC522 хосту **так же, как это
делает ACE2‑Open (Simon‑CR)**: набор операций через упакованный `index` одной команды.
Конечная цель — чтобы встроенные чтение и запись NTAG в multiACE работали на Gen 1
**без правок в multiACE**, то есть чтобы вкладки чтения/записи метки включались его
существующим гейтом «есть туннель».

Зачем: сейчас на Gen 1 штатной меткой читается только заводская Anycubic‑метка; третьи
метки разбираются CFW‑парсером (наш маршрут), но **записать** метку или прочитать
произвольную страницу NTAG из панели нельзя. ACE2 это умеет через туннель.

## 2. Установленные факты (проверено)

**Контракт хоста** (`klippy/extras/ace_rc522.py`, снят с принтера):

```
packed = 0x80000000 | (reader << 24) | ((op & 0xFF) << 16) | ((a1 & 0x3F) << 8) | (a2 & 0xFF)
передаётся как: send_request_to(idx, {'method': 'filament_identify', 'params': {'index': packed}})
reader = 1 if slot >= 2 else 0        # пара антенн внутри устройства
ответ читается как: int(resp['result']['code']) & 0xFF     (resp['result'] — вложенный JSON)
```

| op | операция | параметры | что возвращает |
|---|---|---|---|
| 0 | чтение регистра RC522 | `a1` = регистр | значение регистра в `code` |
| 1 | запись регистра | `a1` = регистр, `a2` = значение | 0 |
| 2 | запись байта в FIFO | `a1` = индекс, `a2` = байт | 0 |
| 3 | команда PCD | `a1` = число tx‑байт, `a2` = команда (`PCD_TRANSCEIVE=0x0C`) | статус |
| 4 | чтение байта из FIFO | `a1` = индекс | байт в `code` |
| 5 | число принятых бит | `a1` = 0 | `0x80` = полный кадр |
| 6 | REQA + anticollision + SELECT | — | 0 = карта в поле |

**Устройство (Gen 1, наш CFW)**

* база — ассет OpenCubic v1.0.2 `ACE_V1.3.863_20260716.bin`, md5
  `9f7b9a678a96caf98d6a08842d3ff971`, 113720 B; наш рабочий образ — md5
  `6148cfc52431fc235536c6d64b5334ef`, 113828 B (4 изменённых + 108 дописанных байт);
  сток для отката — md5 `dcd04589dcadd5b4feab66d33e772531`, 105652 B;
* **таблица команд ACE‑протокола** — пары `{handler, name}` на VA `0x080146xx`,
  имена в `0x080215xx` (`filament_recognition`, `enable_rfid`, `disable_rfid`,
  `get_filament_info`, `set_filament_info`, …). Формат совпадает с тем, что использует
  ACE2, — то есть наш «носитель» не экзотика, а та же механика;
* **`filament_identify` в образе отсутствует** — проверено на живом принтере:
  `ACE_EXT_RAW METHOD=filament_identify …` → `{"code":400,"msg":"InvalidCommand"}`;
* проверенные примитивы считывателя: `read_reg 0x08019D12`, `write_reg 0x08019E1C`,
  опознание `0x0800A6A0`; считыватель — MFRC522‑совместимый (VersionReg = `0xA1`),
  два чипа, пары слотов `1&3` и `2&4` (сосед = `slot xor 2`);
* носитель команды на Gen 1 — `filament_recognition` с упакованным `index`
  (маршрут «мост», чтение/запись регистров и чтение UID уже проверены на стоке);
* запас образа под наш хвост — ~968 байт; врезка `bl` + позиционно‑независимый стаб в
  хвосте — проверенный приём;
* строка версии в нашем форке уже правится (`CV1.3.863`); хвостовая `O` — принятый у
  ACE2‑Open признак «есть туннель», по нему же multiACE считает порог
  `INSERT_MIDPRINT_MIN_FW` (наш формат строки → `(1,3,863)` ≥ `(1,1,47)`, то есть
  гейт «bites while printing» тоже будет вести себя как на туннельном юните).

## 3. Подход: два этапа с ранней проверкой

**Этап A — туннель в нашей врезке (отладка на живом железе).**
Расширяем стаб до всего набора op 0–6, носитель — `filament_recognition`
(проверенный путь). Хост при этом на время отладки правится в одной строке (имя
носителя/поле ответа) — правка **только для тестов**, в upstream не идёт.

**Этап B — настоящая команда `filament_identify` (цель).**
Добавляем в образ имя команды, запись в диспетчер (или обход таблицы) и обработчик с
JSON‑обвязкой, чтобы multiACE работал **без единой правки**. Плюс объявляем версию
`CV1.3.863O` — тогда его гейт сам включает чтение/запись метки, и это заявление
становится правдой.

Этап A даёт быструю проверку самой сложной части (op 2–6 + реальный NTAG), не блокируя
этап B, где основная неизвестность — JSON‑обвязка.

## 4. Неизвестности и пробы (каждая — с критерием приёмки)

* **P1. Точка врезки на CFW.** Найти в обработчике `filament_recognition` место, где
  `index` уже разобран, и убедиться, что врезка `bl` там безопасна (нет побочных
  эффектов, стаб позиционно‑независим).
  *Приёмка:* `ACE_EXT_RAW METHOD=filament_recognition INDEX=<packed op 0 reg 0x37>` →
  VersionReg `0xA1` в ответе, поведение обычных индексов не изменилось.
* **P2. Канал ответа.** Определить, какое поле ответа заполняет обработчик и как отдать
  из стаба один байт значения (на стоке мы отдавали его в `v`).
  *Приёмка:* хост‑драйвер читает это значение как результат операции (в этапе A — с
  правкой поля в отладочной копии; в этапе B — штатное `result.code`).
* **P3. op 2–6.** Реализовать FIFO push/pop, PCD‑команду, RX‑биты и SELECT поверх
  примитивов считывателя; SELECT — через anticollision (`0x93 0x20` → TRANSCEIVE).
  *Приёмка:* `ACE_TAG_READ` на живом NTAG даёт устойчивый UID (два совпадения подряд),
  `ACE_TAG_WRITE` записывает OpenSpool‑запись и она читается обратно.
* **P4. Команда `filament_identify`.** Имя строки, запись в таблицу (перенос таблицы в
  хвост с правкой указателя **или** обход таблицы врезкой), обработчик + JSON‑обвязка
  (`index` из запроса, ответ с `code`/`id`).
  *Приёмка:* multiACE **без изменений** получает ответ на упакованный запрос.
* **P5. Признак туннеля.** Версия `CV1.3.863O`.
  *Приёмка:* multiACE показывает юнит как туннельный (`rc522: true`), вкладки чтения и
  записи метки доступны, `ACE_TAG_READ/WRITE` работают из панели.

## 5. Риски и откат

* **Ассемблер на живом устройстве.** Митигация: каждая правка — отдельный точный
  шаблон, проверка md5/crc16 и дизассемблера до заливки; после заливки — проверки
  `get_info`/`get_status`/`get_filament_info` и разбора метки (регрессия нашего
  маршрута: `rfid = 2`).
* **Откат** — нашим флешером: сток (`dcd04589…`) или база CFW (`9f7b9a67…`),
  md5‑проверенные образы. Никогда не использовать `/etc/init.d/S60klipper
  start|restart` (перезаливает заводскую прошивку); порт освобождать
  `ACE_EXT_FW_RELEASE`/`ACE_EXT_FW_RESUME`; не заливать во время печати.
* **Регрессия парсера.** Наша текущая врезка (`0x08016B9A` + 108‑байтный стаб) остаётся
  нетронутой; туннель — отдельные точки врезки и отдельный хвост.

## 6. Тесты

* офлайн: сборка, md5/crc16, размер и запас, дизассемблерная проверка изменённых
  инструкций;
* на устройстве: `ACE_EXT_RAW`‑пробы (VersionReg, регистры, FIFO), `ACE_TAG_READ` /
  `ACE_TAG_WRITE` на живом NTAG, регрессия — разбор сторонних меток и статус слотов;
* после этапа B: прогон из панели multiACE без host‑правок.

## 7. Что остаётся вне работы

* Правки в upstream multiACE (носитель/гейт) — только если этап B не сложится;
  при удаче этапа B не нужны вовсе.
* Запись MIFARE/Bambu (не NTAG) — вне объёма: хост сам отказывает в записи MIFARE.
